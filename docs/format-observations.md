# FLP format observations

These notes record direct inspection of the bundled `Data/Demo projects/NewStuff.flp` file. They describe one FL Studio 25.2.3.5164 project and are not a claim that every FLP generation uses identical fields.

## Container

The file is 313,356 bytes. Its first 14 bytes decode as:

| Offset | Bytes | Observation |
| --- | --- | --- |
| `0x00` | `46 4C 68 64` | ASCII `FLhd` marker |
| `0x04` | `06 00 00 00` | Header content length is 6 bytes |
| `0x08` | `00 00` | Format field is 0 |
| `0x0A` | `2D 00` | Legacy channel count field is 45 |
| `0x0C` | `60 00` | PPQ field is 96 |
| `0x0E` | `46 4C 64 74` | ASCII `FLdt` marker |
| `0x12` | `F6 C7 04 00` | Event-stream length is 313,334 bytes |

The event stream ends exactly at the end of this file; no trailing bytes are present in this fixture.

## Event observations

The Rust reader found 4,404 event boundaries in this fixture. The first events include:

| File offset | Opcode | Payload | Observation |
| --- | --- | --- | --- |
| `0x16` | `C7` | `25.2.3.5164\0` | ASCII version string; preceding length byte is `0C` |
| `0x24` | `9F` | `2C 14 00 00` | Little-endian value 5164, matching the build suffix in the version string |
| `0x30` | `AC` | `01 01 00` | Three-byte payload; the next event begins at `0x34` |
| `0x34` | `C0` | UTF-16LE text | Begins with the `FL Studio 25...` product/version banner |
| `0x94` | `9C` | `F0 49 02 00` | Little-endian value 150,000; displayed as 150 BPM by the current metadata reader |
| `0xA3` | `11` | `04` | Numerator-like global field, currently displayed as 4 |
| `0xA5` | `12` | `04` | Denominator-like global field, currently displayed as 4 |

The opcode-size rules used by the reader are the conventional four groups visible in the event stream: byte payloads for `00`–`3F`, two-byte payloads for `40`–`7F`, four-byte payloads for `80`–`BF`, and length-prefixed data for `C0`–`FF`. In this fixture, `AC` is a version-specific exception with three payload bytes. Corpus scanning confirms these framing rules across the installed FLP/FST files.

## Project Info observations

In a disposable copy of the installed `Data/Templates/Empty/Empty.flp`, the original FL Studio Project Info dialog exposes Title, Author, Genre, Comments, and Web link. Saving controlled values changed the top-level `0xC2` (title), `0xCF` (author), `0xCE` (genre), `0xC3` (comments), and `0xC5` (web link) data events. The observed modern payloads use UTF-16LE with a two-byte NUL terminator; the empty template stores empty title, genre, author, and comments as `00 00`, and the web-link event is omitted until a value is entered. The event stream places these fields before the first `0x40` channel marker.

The Rust model reads all five strings, retains empty values as empty strings, and edits only the selected field events while preserving their terminator convention, bytes after the terminator, and every unrelated event. For absent fields it inserts a new length-prefixed event before the first channel marker. Legacy projects use the repository's existing version-based Windows-1252 string rule. A controlled FL Studio reopen of the Rust-written disposable project displayed the edited title, author, genre, comments, and web link. Legacy encoding behavior is covered by synthetic fixtures rather than an installed old-version FL Studio oracle.

## Project settings observations

Controlled toggles in FL Studio 26.1.6 Project settings > Project > Advanced mapped two options. `Fast declick for cut groups` is a one-byte `0x28` event in the recognized settings sequence; payload `01` means enabled and `00` means disabled. `Play truncated notes in clips` defaults to enabled when the zero-valued word event `0x64 00 00` is absent; adding that event immediately before the sequence disables the option. The surrounding sequence begins with `0x1D 01`, `0x27 01`, then `0x28`, followed by `0x1F 00`, `0x26 01`, and `0x67 12 00`.

The Rust model, CLI, and desktop dialog only edit this recognized event block, preserve unrelated events, and reject files where the block is missing or ambiguous. Sampler and VST3 Pattern Clip playback honor `Play truncated notes in clips`: when enabled, a note that starts inside a clip keeps its scheduled note-off beyond the clip end; when disabled, the note-off is clamped to the clip end. Image-Line documents the option as restoring notes that span a slice point in Pattern Clips ([Project Settings manual](https://www.image-line.com/fl-studio-learning/fl-studio-online-manual/html/songsettings_settings.htm)). The scheduling behavior has not yet been compared against a native render. These event mappings were verified against one FL Studio 26.1.6 project; other project settings, older-version layouts, and behavior across a broader project corpus remain to be mapped.

The project-level `0x17` byte event stores pan law: `0` means Circular and is the default; `2` means Triangular. This mapping is cross-checked against the independent [flpdiff FLP format specification](https://github.com/dawhubapp/flpdiff/blob/main/docs/fl-format/flp-format-spec.md), which reports non-default values in its FL 25 corpus. It has not yet been confirmed against a controlled native FL Studio toggle. The Rust model retains any raw byte, and the CLI and desktop Project Settings dialog can edit it; when the event is absent, the default Circular value is reported and a non-default edit inserts the event before channel data. Image-Line describes Circular panning as equal-power with a 3 dB center dip, while Triangular panning uses no center compensation ([Project Settings manual](https://www.image-line.com/fl-studio-learning/fl-studio-online-manual/html/songsettings_settings.htm)). Supported mono audio clips, Sampler voices, and mono VST3 sources use equal-power Circular or linear Triangular gains inferred from that description during Playlist playback and rendering. The exact coefficients, stereo-source balance panning, and native Mixer track panning remain unverified by controlled native render comparison.

Image-Line's [Project Settings manual](https://www.image-line.com/fl-studio-learning/fl-studio-beta-online-manual/html/songsettings_settings.htm) describes a project-wide time signature separately from Playlist and Pattern time signatures. The independent [flpdiff FLP format specification](https://github.com/dawhubapp/flpdiff/blob/main/docs/fl-format/flp-format-spec.md) identifies the global numerator and denominator as one-byte `0x11` and `0x12` events. The Rust model, CLI, and Project Settings dialog read and edit a unique, nonzero global pair, inserting missing bytes before the first channel event and preserving channel-scoped or unrelated events. The [Piano roll manual](https://www.image-line.com/fl-studio-learning/fl-studio-online-manual/html/pianoroll.htm) confirms that custom and multiple signatures belong to individual Patterns. PyFLP's [Pattern event model](https://pyflp.readthedocs.io/en/latest/_modules/pyflp/pattern.html) scopes time-marker events to `0x41` Pattern IDs; its [time-marker model](https://pyflp.readthedocs.io/en/latest/_modules/pyflp/timemarker.html) maps the position to `0x94` and meter fields to one-byte `0x21`/`0x22`. This implementation reads, sets, and deletes Pattern signatures by tick and paints meter changes in the Piano roll grid. Pattern records and signatures have not yet been verified against a controlled native save.

## Channel Rack swing observations

Image-Line documents global swing as a 0–100% Channel Rack amount, with each channel's swing setting acting as a multiplier of the global value; both amounts must be above zero for swing to take effect ([Channel Rack manual](https://www.image-line.com/fl-studio-learning-content/fl-studio-online-manual/html/channelrack.htm)). PyFLP identifies global swing as project-level event `0x0B`, stored in one byte with a 0–128 range and a default of 0 ([PyFLP Channel Rack model](https://pyflp.readthedocs.io/en/v2.1.0/_modules/pyflp/channel.html)).

The Rust model reads and edits the project event, inserts it before the first channel marker when needed, and preserves unrelated events. `global-swing`, `set-global-swing`, and the Channel Rack header menu expose this value. Channel swing remains separately stored as the per-channel `0x61` word multiplier. Sampler and VST3 Pattern playback now combine the global amount and source-channel multiplier, delaying aligned even-numbered 16th-step onsets by up to one third of a step. Image-Line documents the alternating 16th-step behavior and the channel multiplier, but not the exact maximum tick offset; triplet placement is an inference that still needs comparison with native FL Studio renders. Audio clips and off-grid note positions are not swung, and note durations remain unchanged.

## Pattern creation observations

The pattern model recognizes word-sized `0x41` pattern IDs and treats an immediately following `0xD0` or `0xE0` data event as that pattern's 24-byte note records. Empty-pattern creation locates score sections by those adjacent marker/note-event pairs, reuses their unique note-event opcode, and chooses the next ID after the highest marker in those sections. This avoids confusing repeated `0x41` markers in later Playlist track records with score patterns. The new marker and zero-length note event are inserted at the end of the last recognized score section. A Rust-created pattern 15 in the installed `Electric Loop - The Ogun Dream.flp` demo project re-parsed as an empty pattern, and synthetic round-trip fixtures preserve unrelated events. The modified project has not yet been opened in FL Studio, so the insertion strategy still needs native validation.

## Channel grouping observations

The stream contains 45 `0x40` markers, matching the header's channel count. At the first marker, the following fields occur before the next channel marker: a one-byte `0x15` value of `2`, a UTF-16LE `0xC9` string `Harmless`, and a UTF-16LE `0xCB` string `Synth Bass`. A later one-byte `0x00` event carries `1`. Across all 45 groups, the `0xCB` text produces plausible channel labels such as `Grv Kick 27`, `Piano Dark`, and `TEMPO`; `0xC9` produces plugin labels such as `3x Osc` and `FLEX` where present.

The current reader therefore presents `0x40` groups as channel summaries, treating `0x15` as kind, `0x00` as enabled, `0xC9` as plugin identifier, and `0xCB` as display name. A same-length controlled rename of the `Synth Bass` channel to `Synth Test` changed the exported MIDI track name accordingly, confirming the `0xCB` mapping. The complete event ranges remain accessible for later decoding.

For channel kind `4` in the `Ookay - Thief.flp` demo project, the `0xC4` data event decodes as a UTF-16LE sample source path. Channel 29 (`Main Vox`) stores `%FLStudioFactoryData%\Data\Patches\Misc\Used by demo projects\Ookay - Thief\ookay thief vox.wav`, and the referenced file exists in the installation's `Data` tree. The same `0xC4` path event is used by kind-0 Sampler channels; this is documented by [PyFLP's channel event reference](https://pyflp.readthedocs.io/en/stable/reference/events.html) and sampler model. The Rust channel summary now exposes paths for kinds 0 and 4 while retaining original event bytes, and the decoder continued to exclude plugin channel payloads. A sweep of the installed 165-project corpus found 410 kind-0 Sampler channels with a decoded sample path. The sample resolver expands the factory-data macro using configured or discovered installation roots and resolves project-relative paths. The `sample-paths` command resolved all 32 media references in `Ookay - Thief.flp`. The `audio-info` command decodes WAV, Ogg/Vorbis, FLAC, MP3, AIFF, and lossless mono/stereo WavPack media by content. Some factory samples use ordinary Ogg data directly, others use a private RIFF/WAVE header whose `data` chunk begins with `OggS` at offset 54, and `Riser Noise.wv` uses a WavPack stream with an embedded RIFF wrapper. All three forms decoded locally. `render-audio-clips` makes an experimental offline stereo mix of enabled audio-channel Playlist clips using base tempo and source offsets; it skips clips with non-default scale because the meaning of that field is not confirmed. On this local project, the render completed 1,304 clips from 23 sample files, skipped 47 scaled clips, and wrote a valid 230.4-second float WAV. Playlist and Sampler playback call the same content-sniffing decoder, so the wrapped-Ogg path is used before their bounded device streams as well as by offline rendering. Offline and live mixes apply a provisional volume/pan mapping based on observed raw defaults; native output comparison is still needed. Live transport mixes in bounded 1,024-frame blocks and streams to the selected device. The decoder holds up to 512 MiB of distinct sources in memory, while offline mixing has a separate 512 MiB limit.

The selected-pattern Sampler preview turns kind-0 notes into sample-frame events, decodes each referenced sample once, resamples for the output rate and note key using the selected live quality (24-point sinc when no preference is saved), applies velocity, note pan, and provisional channel gain/pan, and streams in 1,024-frame blocks through the existing device stream. Note pan values 0–128 are centered at 64 and are applied as offsets from channel pan before the project pan law; this combination is inferred and awaits a native render comparison. The same per-note pan is used by Playlist playback and rendering. Its voice pool defaults to 64 and steals the oldest active voice when full. In the installed `Asher Postman - Future House.flp`, pattern 1 includes six kind-0 Sampler notes across three channels and three sample files; all six sample notes have zero duration in their FLP note records. The prototype treats zero-duration Sampler notes as one-shot triggers that play to sample end. That playback meaning is an inference from the record shape and sample-channel role, pending comparison against FL Studio's rendered output. The offline command produced an 84,360-frame stereo WAV at 44.1 kHz (1.913 seconds). Playlist transport now places supported Sampler notes by Pattern Clip position, repeats them using the explicit pattern length or an inferred note span, and clips keyed-note ends at the clip boundary. PyFLP maps the saved Sampler root note to `0x87`, Reverse to bit 1 of the `0x46` FX-flags word, UsesLoopPoints to bit 3 of the `0x8F` sampler-flags dword, and Ping-pong to channel event `0x14`; Image-Line documents reverse, loop-point playback, and ping-pong behavior ([PyFLP channel model](https://github.com/demberto/PyFLP/blob/master/pyflp/channel.py), [Image-Line Sampler manual](https://www.image-line.com/fl-studio-learning/fl-studio-online-manual/html/chansettings_sampler.htm)). The Rust Sampler renderer honors Reverse and, when UsesLoopPoints is enabled, reads the first loop in a standard WAVE `smpl` chunk or the AIFF `INST` sustain loop resolved through `MARK` frame positions; WAVE loops use the saved ping-pong flag, while AIFF forward/backward loops follow their `playMode`. When a keyed note enters the existing generic 10 ms release ramp, a valid AIFF `INST` release loop replaces the sustain loop and uses its forward or forward/backward mode. This is a provisional short release phase because FL Sampler envelope release timing is not yet applied; manual FL-specific markers remain unsupported. These mappings have not been validated against a native save/render. A valid saved channel root (`0x87`) is preferred; when absent or invalid, WAVE `inst` or AIFF `INST` metadata supplies the root key before the `smpl` MIDI unity note, then C5. WAVE `inst` `chFineTune` adds signed cents, falling back to the `smpl` MIDI pitch fraction when no valid `inst` tuning is available; AIFF `INST` detune adds signed cents. Signed WAVE `inst` `chGain` and AIFF `INST` gain fields are applied as sample gain in decibels. Valid ordered WAVE/AIFF instrument key ranges and 1–127 velocity ranges filter Sampler notes before scheduling, matching Image-Line’s documented low/high sample properties for the Channel Sampler ([sample properties](https://cluster.image-line.com/fl-studio-learning/fl-studio-online-manual/html/plugins/Edison_14.htm)) and the AIFF velocity range definition ([AIFF 1.3 specification](https://blog.zamzar.com/wp-content/uploads/2014/10/aiffspecs.pdf)). AIFF `INST` base note zero is ignored, matching Image-Line’s documented behavior ([What’s New](https://www.image-line.com/fl-studio-learning/fl-studio-beta-online-manual/html/WhatsNew.htm)). Native FL Studio save/render comparison remains open. The `inst`-before-`smpl` root-key and fine-tune precedence is based on the WAVE fields and still needs native comparison. The persisted Audio settings Read sample root note preference defaults on and controls whether WAVE or AIFF root-key metadata is used; sample fine tuning and WAVE `inst` or AIFF `INST` sample gain remain applied, and a valid saved `0x87` channel root still takes precedence. Envelopes, source offsets, native timing/level comparison, and Mixer effects are also incomplete.

The Sampler precomputed Fade Out (`0x4B`) and Fade In (`0x4C`) fields are 0–1024 values and Image-Line describes them as quick processing fades over sample data ([Sampler Channel manual](https://www.image-line.com/fl-studio-learning/fl-studio-online-manual/html/chansettings_sampler.htm)). An Image-Line forum explanation describes Fade In as attenuation at the sample start and Fade Out as attenuation at the end across the sample ([discussion](https://forum.image-line.com/viewtopic.php?t=151347)). The Rust renderer uses raw/1024 as attenuation at the corresponding endpoint and linearly tapers the sample data before resampling; invalid saved values are ignored. The exact native gain curve and its interaction with looped samples still need comparison.

Sampler Envelope/LFO data appears in channel event `0xDA` as five ordered records: Panning, Volume, Mod X, Mod Y, and Pitch. Based on the pinned [PyFLP channel parser](https://github.com/demberto/PyFLP/blob/f937126b888ce94271bfea631b89166c74056530/pyflp/channel.py), each record has a flags dword at payload offset 0 and an enabled dword at offset 4. Envelope predelay, attack, hold, decay, sustain, release, and amount dwords are at offsets 8, 12, 16, 20, 24, 28, and 32. LFO predelay, attack, amount, speed, and shape fields occupy offsets 36, 40, 44, 48, and 52; attack, decay, and release tension dwords are at offsets 56, 60, and 64. PyFLP maps flags bit 0 to envelope tempo sync, bit 1 to LFO tempo sync, and bit 5 to LFO phase retrigger. It documents raw ranges of 100–65536 for envelope and LFO predelay/attack/hold/decay/release time values, 200–65536 for LFO speed, 0–128 for sustain, −128–128 for envelope/LFO amounts and tensions, and shape codes 0 Sine, 1 Triangle, 2 Pulse. These offsets, meanings, and ranges come from a third-party parser; a controlled FL Studio save comparison has not been performed.

The Rust channel model decodes all five ordered records, and its API, CLI, and Channel Rack editor update the recognized fields while preserving unknown flag bits, unedited fields, trailing payload bytes, and unrelated events. The saved Volume-envelope enabled flag controls Sampler note-off behavior: when disabled, playback continues through the sample after note-off and leaves the sustain loop; when enabled, supported timing fields drive linear pre-delay, attack, hold, decay, sustain, and release stages, with unsupported data falling back to the generic release ramp. Image-Line documents both behaviors and the Volume envelope's global signed Amount multiplier and Sustain level ([Sampler Channel manual](https://www.image-line.com/fl-studio-learning-content/fl-studio-online-manual/html/chansettings_sampler.htm), [Envelope / Instrument Channel Settings](https://www.image-line.com/fl-studio-learning/fl-studio-online-manual/html/chansettings_ins.htm)). The renderer maps each normalized envelope level `L` through `clamp(1 + (amount / 128) * (L - 1), 0, 2)`, using PyFLP's documented amount range −128…128 and sustain range 0…128. This applies saved sustain even when the pre-delay, attack, hold, and decay are at raw 100. Non-minimum raw times use a candidate conversion visible as an intermediate calculation in [SatyrDiamond’s public parser](https://github.com/SatyrDiamond/flp-parser/blob/main/flp_parser_20.py#L971-L979): `seconds = (((raw - 100) / 65436) * 6)^2`, producing 0–36 seconds over the documented raw range. That parser returns the original raw value instead of the calculated result, so this candidate mapping is not validated by the parser. The conversion and linear stage curves are implementation inferences and still need native render comparison; tempo synchronization and attack/decay/release tension curves are not applied. All LFO modulation remains unsupported ([PyFLP Envelope fields](https://github.com/demberto/PyFLP/blob/f937126b888ce94271bfea631b89166c74056530/pyflp/channel.py)).

The channel `0xDD` data event stores Max Polyphony as a 32-bit value at payload offset 0, Slide at offset 4, and a flags byte at offset 8; PyFLP identifies flag bit 0 as Mono and bit 1 as Porta ([PyFLP channel parser](https://pyflp.readthedocs.io/en/v2.1.0/_modules/pyflp/channel.html)). The Rust channel summary exposes the raw maximum, Mono, and Porta state. Sampler playback applies a nonzero maximum by stopping the oldest voice on that channel when the limit is reached; zero is provisionally treated as unrestricted. Mono releases existing unreleased voices on the same channel, allowing the existing release behavior to overlap, and takes precedence over Max Polyphony. These behaviors follow Image-Line's description of Max Poly and Mono ([Miscellaneous Channel Settings](https://www.image-line.com/fl-studio-learning/fl-studio-online-manual/html/chansettings_misc.htm)); raw unrestricted encoding and release timing still need native save/render comparison. Supported Sampler Pattern, Playlist, and live MIDI paths now glide a newly started voice from the pitch, velocity, and pan of the latest still-held voice on that channel when Porta is enabled, or when Mono notes overlap. Slide duration uses an inferred fourth-power mapping calibrated against PyFLP's documented raw default (820, approximately half a step) and maximum (1660, eight steps); the raw mapping and voice-retrigger behavior need controlled native render comparison. Playlist glide endpoints use the arrangement tempo map, so tempo changes during a glide affect its overall duration; the pitch trajectory through each tempo change still needs native comparison. Cutoff and resonance transitions remain unsupported.

The channel `0x84` dword stores a pair of 16-bit values `(Cut, Cut by)` ([PyFLP channel model](https://pyflp.readthedocs.io/en/v2.1.0/_modules/pyflp/channel.html)). `ChannelSummary` exposes the raw pair. On supported Sampler playback paths, a newly triggered channel with a nonzero Cut value stops existing Sampler voices whose Cut by value matches it; zero is provisionally treated as unassigned. When the saved project Fast Declick option is enabled, the old voice instead receives a provisional 10 ms cosine fade before being stopped. Image-Line says this option selects Transient (no bleeding) declicking for Samplers in Cut Groups ([Project Settings manual](https://www.image-line.com/fl-studio-learning/fl-studio-online-manual/html/songsettings_settings.htm)); matching its filtering fade and native Cut timing still needs render comparison. VST3 channel Cut/Cut by behavior remains unsupported.

## Pattern and Piano roll note observations

Pattern identity is carried by `0x41` word events. In the FL 25.2.3 NewStuff project, note-bearing `0x41` events are immediately followed by `0xE0` data events. Their payload lengths are multiples of 24 bytes. Reading each record as a little-endian position, flags, channel id, length, key, group, and byte-sized note properties yields 213 stored notes across pattern ids 1, 2, 3, 4, 6, 7, and 8. The first four records in pattern 1 (positions 0, 384, 768, and 1,152; keys 47, 44, 49, and 39; length 384; velocity 100) match the original MIDI export's Synth Bass note-on/off events at ticks 0–384, 384–768, 768–1,152, and 1,152–1,536. The installed FL 10.9.0 `Charles Deluxe - Performance Demo.flp` also uses a 1,440-byte `0xE0` payload after pattern id 1, yielding 60 records across channel ids 11 and 12. This corpus evidence contradicts a simple rule that `0xE0` is only used starting in FL 25; the reader therefore checks the pattern marker context and accepts `0xD0` or `0xE0` rather than selecting an opcode solely by version. NewStuff's MIDI export contains 2,505 note spans, far more than its 213 stored note records. Pattern Clips now schedule Sampler notes using the decoded `pattern_base`/`item_index` relationship and clip position/length. Repeat length prefers the explicit pattern length event and falls back to a positive note span; the exact repeat and edge behavior remains an inference until compared with native FL Studio playback.

Hosted VST3 Pattern and Playlist notes apply the saved per-note pan when the loaded instrument advertises VST3 Pan through `INoteExpressionController`. The host gives each scheduled note a unique VST3 note ID, sends its NoteOn with the existing fine-pitch tuning, then sends Pan at the same sample offset; its NoteOff uses the same ID. Raw FL note-pan values 0–128 map to normalized VST3 values 0.0–1.0, with 64 at center. Image-Line's Piano roll API documents the note-pan direction/default, and Steinberg defines Pan as a bipolar VST3 note-expression dimension ([Image-Line Piano roll Scripting API](https://www.image-line.com/fl-studio-learning-content/fl-studio-online-manual/html/pianoroll_scripting_api.htm), [Steinberg VST3 Note Expression](https://steinbergmedia.github.io/vst3_dev_portal/pages/Technical%2BDocumentation/Change%2BHistory/3.5.0/INoteExpressionController.html)). Plugins that do not advertise Pan receive no note-expression events. This mapping and audible behavior still need comparison against an FL Studio render.

Hosted VST3 Pattern and Playlist note-offs carry FL's per-note release property as VST3 NoteOff velocity, mapping raw FL values 0–128 to normalized values 0.0–1.0. Image-Line documents release as a 0.0–1.0 note-release velocity and identifies supported native synths; Steinberg defines VST3 NoteOff velocity as 0.0–1.0 ([Image-Line Piano roll Scripting API](https://www.image-line.com/fl-studio-learning/fl-studio-online-manual/html/pianoroll_scripting_api.htm), [Image-Line Piano roll manual](https://www.image-line.com/fl-studio-learning/fl-studio-online-manual/html/pianoroll.htm), [Steinberg VST3 NoteOffEvent](https://steinbergmedia.github.io/vst3_doc/vstinterfaces/structSteinberg_1_1Vst_1_1NoteOffEvent.html)). A VST3 instrument controls how it uses release velocity. This mapping has not been compared against native FL Studio rendering.

The 10.9.0 sample stores pattern names as single-byte Windows-1252 text, while the 25.2.3 sample stores them as UTF-16LE. The current string decoder switches at FL 11.5 based on a public parser changelog; no installed project around that boundary was found, so it remains unconfirmed locally ([PyFLP changelog](https://github.com/demberto/PyFLP/blob/master/CHANGELOG.md)). Pattern names and note counts are readable for the two local fixtures; note timing and property fields have not yet been compared against the original Piano roll display. The official manual describes the Piano roll as channel-targeted note data within patterns and notes that Playlist Pattern Clips arrange those patterns on the timeline ([Piano roll](https://www.image-line.com/fl-studio-learning-content/fl-studio-online-manual/html/pianoroll.htm), [Patterns](https://www.image-line.com/fl-studio-learning-content/fl-studio-online-manual/html/playlist_patterns.htm)). A public reverse-engineered record layout was used as a cross-check, but local FL 10.9 bytes take precedence where the two disagree ([format reference](https://github.com/dawhubapp/flpdiff/blob/main/docs/fl-format/flp-format-spec.md)).

Public reverse-engineered format references identify Pattern event `0xDF` as a stream of 12-byte controller records: 32-bit position, two reserved bytes, raw channel and flags bytes, then a 32-bit float value. The model preserves these fields, including the exact float bits, and the CLI can inspect and edit individual records. The API, CLI, and Piano roll Events lane can also draw/paint a stream that already has a record: values at existing ticks update the first matching point, while new ticks copy the first stream record's reserved/channel/flags bytes. Draw uses snap unless Alt is held, and Shift holds the starting value during Draw or Paint strokes. The Interpolate tool updates selected interior values between the first and last selected points without changing positions or opaque bytes; left-drag is linear and right-drag uses a cubic smoothstep curve because Image-Line does not publish the spline equation. The CLI accepts comma-separated `tick:value` pairs and explicit raw channel/flags bytes, and can linearly or smoothly interpolate existing stream points in an inclusive range. A range erase through the API, CLI, or lane removes only matching stream records and retains unrelated records and event bytes. The channel/flags meaning, target parameter mapping, and native-save verification are still unknown; the Piano roll's documented event controls do not establish this binary mapping ([format reference](https://github.com/dawhubapp/flpdiff/blob/main/docs/fl-format/flp-format-spec.md), [Piano roll Scripting API](https://www.image-line.com/fl-studio-learning-content/fl-studio-online-manual/html/pianoroll_scripting_api.htm)).

PyFLP identifies bit 3 of the 16-bit note flags as the Slide flag. The selected-note editor exposes a dedicated toggle that changes only this bit, and the Piano roll draws a start marker for flagged notes. Image-Line documents that slide notes affect overlapping native FL Studio notes in the same note-color group, use the highest note in the chord as the reference, reach the target pitch at the slide-note end, and leave the held notes at that pitch afterward; a slide note on its own produces no sound. Supported Sampler preview, Playlist, and render paths apply pitch, velocity, and pan slides to active voices in the same saved MIDI color group. Pitch uses per-note fine pitch and targets the slide note's Piano roll pitch relative to the highest sounding note at slide start; velocity is interpolated as a linear gain factor and pan linearly interpolates the saved 0–128 note-pan value before the existing channel-pan mapping. Slide-aware voice-end simulation includes one-shot tails under downward glides. The pitch and property curves need native render comparison; cutoff, resonance, and other note properties remain open. Image-Line says this Piano roll slide feature does not apply to VST instruments ([Piano roll manual](https://www.image-line.com/fl-studio-learning/fl-studio-online-manual/html/pianoroll.htm), [Slide Notes and Per Note Parameters on VSTs](https://support.image-line.com/action/knowledgebase?ans=592)). Image-Line's Piano roll scripting API also exposes a writable muted property and says muted notes do not play. This implementation maps mute to candidate note-flag bit 0, toggles it from the Mute tool and selected-note editor, and excludes marked notes from supported playback and MIDI export. The mute-bit mapping has not been validated against a native save. The per-note Porta flag is byte 19 bit `0x10`; the low nibble of that byte remains the note color/MIDI channel. A decompilation-based analysis reports that this bit inverts the channel's Porta setting and that a preceding note must exist in the same group. The API exposes the flag and low-nibble MIDI channel separately, the selected-note editor can toggle Porta, the Piano roll draws a ring marker for flagged notes, and `set-note-porta` edits it from the CLI. Supported Sampler Pattern and Playlist paths apply a pitch, velocity, and pan transition from the last triggered note in the same group when the effective Porta setting is on, retaining its values after its voice ends. VST3 hosts ignore the flag, matching Image-Line's native-instrument-only description; MIDI export uses only the low nibble. The encoding and inversion are cross-checked against an independent [FLP analysis](https://github.com/Ka1-S/LYNX/blob/main/docs/analise/REA_rodada6.md) and [note-record model](https://github.com/Ka1-S/LYNX/blob/main/src/flp/Flp.h), while Image-Line documents the [Piano roll Porta behavior](https://www.image-line.com/fl-studio-learning/fl-studio-online-manual/html/pianoroll.htm). The transition curve and resulting render still need comparison against FL Studio.

Image-Line's [Scale Levels tool](https://www.image-line.com/fl-studio-learning-content/fl-studio-online-manual/html/pianoroll_scale.htm) adjusts velocity data with Center, Tension, Multiply, and Offset controls. The desktop and project API expose all four documented ranges for selected notes or the target channel. Center shifts a local pivot by up to 127 velocity units in either direction, Tension bends distances from that pivot with a bounded logarithmic curve, Multiply scales around the pivot, and Offset adds to the result. These formulas follow the manual's descriptions but have not been compared with FL Studio's exact response. Changes touch only the velocity byte at offset 21 in each 24-byte score record.

Image-Line's [Piano roll Limit tool](https://www.image-line.com/fl-studio-learning/fl-studio-online-manual/html/pianoroll_limit.htm) supports a key/scale restriction and Up, Down, or Alternate snapping for pitches outside that scale. The rewrite can apply the selected Piano roll key and scale after folding/clamping targeted note pitches into the configured range. Up and Down choose the next in-range scale pitch in that direction, falling back to the opposite direction at a range edge; Alternate switches direction between successive out-of-scale notes in the target scope. With Wrap to lowest octave enabled, pitches map into the lowest octave of the configured range while preserving pitch class, then clamp if that octave has no matching key. This follows the manual's description; exact alternate-snap edge behavior has not been compared with native FL Studio.

Image-Line's [Articulate tool](https://www.image-line.com/fl-studio-learning/fl-studio-beta-online-manual/html/pianoroll_articulate.htm) documents note-length Multiply, Variation and Seed, Use lengths, Only with selection, chord chopping, and quick presets for Legato, Portato, Staccato, a small gap, or chord chopping alone. The API and Piano roll implement the 10–100% length multiplier, original-length scaling, next-onset legato boundaries, selected-only context, repeatable seeded variation, and optional overlap trimming at the next distinct onset. The Options menu offers those presets; its Portato and small-gap settings use local 90% and 98% legato multipliers pending comparison with FL Studio. Variation currently uses a signed offset up to the configured percentage of the calculated duration; its distribution has not been compared with FL Studio. Edits touch only the 32-bit note length at offset 8 in each score record.

Image-Line's [Riff Machine](https://www.image-line.com/fl-studio-learning/fl-studio-online-manual/html/pianoroll_riff.htm) describes an eight-stage progression, chord, arpeggiation, mirror, levels, articulation, groove, and fit workflow, with an option to work on an existing score. The rewrite implements a selected-scope subset: it can use a loaded `.fsc` score as a normalized Note Progression pattern, uses the lowest note at each onset as the progression root, builds diatonic triads or applies custom score voicings, arpeggiates them, applies seeded velocity variation and length scaling, then fits pitches to the selected scale and range. The progression and chord score pickers open the installed FL Studio preset folders when detected, but the score files are not bundled; exact native voicing remains unimplemented or unverified; the Piano roll can preview sound through any stage using an isolated project copy without committing edits; custom chord score groups are transposed by their lowest pitch and cycled across progression roots as a local interpretation.

Image-Line's [Piano roll Claw Machine](https://www.image-line.com/fl-studio-learning/fl-studio-online-manual/html/pianoroll_claw.htm) defines a repeating Period, Trash every, Time distortion, Remove short notes, and Stretch to compensate. The rewrite exposes those controls for channel or selected notes: it divides each period into 16 slices, removes note onsets on every Nth slice, warps surviving onsets toward the period start or end with a mirrored power curve, optionally removes notes shorter than one slice, and extends surviving notes across gaps containing removed onsets. It edits existing score records only; note splitting/creation, the native slice pattern, distortion curve, and short-note threshold remain unverified.

## Playlist clip observations

The FL 25.2.3 NewStuff project has an explicit arrangement marker at event 2257: `0x63` carries arrangement id 0, and the following `0xF1` event contains the UTF-16LE name `Arrangement`. Event 2260 (`0xE9`) carries 119,520 bytes, exactly 1,494 records of 80 bytes each. The first record begins with position 0, pattern base `0x5000`, item index 29, length 30,816, raw track index 471, group 0, and flags `0x0040`. The last 16 bytes contain a scale value of 1.0 plus eight trailing bytes. Records retain their original bytes in the event stream.

The FL 21–24 60-byte layout has a legacy `float32` scale somewhere in its tail according to the independent [flpdiff format notes](https://github.com/dawhubapp/flpdiff/blob/main/docs/fl-format/flp-format-spec.md). In the available FL24 project with 146 clips, bytes 52–55 decode as `1.0` for every record, so the reader and editor now treat that location as the legacy scale field. No non-default FL24 scale example or controlled native save comparison is available here; non-unit values remain unsupported by playback and rendering, and the exact mapping remains a candidate.

The installed FL 10.9.0 Charles Deluxe project has no `0x63` arrangement marker. Event 531 (`0xE9`) contains 1,152 bytes, exactly 36 records of 32 bytes, embedded before the final `0x62` channel boundary. The reader treats such unmarked records as the implicit arrangement id 0. Its record prefix uses the same position, base, item, length, raw-track, group, unknown-word, flags, four opaque bytes, and two float fields at offsets 0 through 31; unlike the newer record it has no clip id or scale field. One legacy clip refers to pattern id 1 through item index `0x5001`.

For NewStuff, clip `item_index` values at or above `pattern_base` resolve to pattern ids by subtraction; lower values resolve to channel ids. For example, clip item 29 points to channel 29 (`Main Vox`) while its visible Playlist row is named `Thief Vox`. Item 34 points to channel 34 (`MELODICS #2`), which is an automation channel. This distinguishes the clip's source object from the Playlist row that contains it. The current API resolves these as pattern or channel targets and retains the separate row name.

Project version tags do not reliably identify the `0xE9` record width. For example, `DEDZII - NIGHT TERROR.flp` has tag `24.2.99.4844` but a 123,200-byte event that decodes as 1,540 80-byte records; `Treben - Umziky - All the same.flp` has tag `20.99.3000.3213` but a 6,480-byte event that decodes as 108 60-byte records. The parser considers each divisible width (32, 60, 80, and 88) and scores shared header consistency, raw track range, and nonzero lengths. It uses the version tag only when those structural signals do not clearly distinguish candidates, and still rejects unresolved ambiguity. The decoded visible track number uses the reference's `499 - raw_track_index` mapping, while retaining the raw value.

An independent [FL Studio 2026 Playlist format analysis](https://github.com/clarkipeng/flpkit/blob/main/src/flpkit/formats/playlist.py) identifies bytes 24–31 of its 88-byte records as a tick source cut window. A window starting at tick 0 and ending at the clip length appears to represent an uncut clip whose visible length is stored in the common header. New 88-byte Pattern Clips created by the rewrite initialize that window to `[0, length]`. Resizing is enabled only for this recognized full-window Pattern Clip shape and changes the common length plus the window end while preserving other bytes. This mapping is third-party reverse engineering, and no FL Studio 2026 `.flp` fixture is available in the current checkout for native-save validation. Audio Clip tick-to-source conversion remains unknown.

The same NewStuff event stream contains 500 Playlist track records (`0xEE`, 70-byte payloads). Each record is followed by an optional one-byte `0x2B` event and a `0xEF` UTF-16LE name. The decoder retains the 70-byte state payload and the adjacent byte without assigning undocumented meanings. Track records are numbered from one; a clip's decoded zero-based row maps to that identifier by adding one. For example, the first Playlist clip has raw track index 471, decoded row 28, and resolves to Playlist track id 29, `Thief Vox`, which matches the label in FL Studio. The next clip resolves to `MELODICS #2`. This confirms the clip-to-track-name association for this project but does not yet decode the rest of the `0xEE` state.

PyFLP maps channel Reverse to bit 1 of the channel's `0x46` FX-flags word and identifies kind 4 as the Audio Clip channel ([PyFLP channel model](https://pyflp.readthedocs.io/en/stable/_modules/pyflp/channel.html)). The reader, API, CLI, and Channel Rack expose that flag for sample-backed channels, and Playlist Audio Clip playback/render reverses the selected source window for kind 4. Combined, Stereo, and Spectral Playlist waveform previews also mirror the selected source window's time direction when Reverse is enabled. Image-Line documents a separate per-instance Reverse in Clip Properties and **Reverse selected audio clips** in the Playlist ([Audio Clips manual](https://www.image-line.com/fl-studio-learning/fl-studio-online-manual/html/playlist_audioclip.htm), [Playlist manual](https://www.image-line.com/fl-studio-learning-content/fl-studio-online-manual/html/playlist.htm)). The Playlist edit currently emulates independent state by copying the kind-4 channel and retargeting the selected clip when the channel is shared; it does not map the native per-instance variant record. Both the channel flag inference and native per-instance representation still need controlled save and render comparison.

## Automation observations

Scanning the 165 installed `.flp` projects found 1,105 kind-5 channels across 49 projects. Every observed channel had an `0xEA` data event. Each payload has a 17-byte opaque header, a little-endian point count at byte offset 17, then 24-byte point records starting at offset 21. The records decode as an eight-byte position delta in beats, an eight-byte normalized value, a four-byte tension value, and four opaque bytes. Positions are cumulative from the start of the clip. This layout agrees with an independent [FLP automation decoder](https://github.com/clarkipeng/flpkit/blob/main/src/flpkit/formats/automation.py); the installed corpus's declared counts yielded 9,785 point records.

All 1,105 blobs fit the declared point count. Of these, 1,103 had a 112-byte era trailer and two had a 136-byte trailer. The finite normalized values observed ranged from 0 through 1.0000403; finite tensions ranged from -1 through 1. The point reader retains each four-byte point tail, while the source event remains untouched in the document. The edit API can change an existing point's position, value, or tension; moving a point adjusts its stored delta and the following point's delta, preserving subsequent absolute positions. Insertions and removals update the point count and adjacent delta while retaining the opaque header, all unmodified point records, and the era trailer. New points currently use four zero bytes for the opaque point tail. The desktop Automation view displays type-5 curves and writes edits through the same lossless API; the API, CLI, and editor can fill interior point values linearly or with cubic smoothstep while retaining point positions, copy the complete `0xEA` state payload between type-5 channels, flip or normalize the point values, and apply the Center/Tension/Multiply/Offset Scale Levels controls. The Level Scale tool documents Automation Multiply at -200% to 200%; the implementation uses a local bounded logarithmic tension transform aligned with the existing Piano roll Scale Levels tool, while the Automation parameter ranges and exact response still need native comparison ([Automation Level Scale tool](https://www.image-line.com/fl-studio-learning/fl-studio-online-manual/html/plugins/envelopetools_scalelevel.htm), [Piano roll Scale Levels](https://www.image-line.com/fl-studio-learning/fl-studio-online-manual/html/pianoroll_scale.htm)). Copying replaces an existing target blob or inserts one for a target without a blob, retaining the source's opaque header, LFO amount, point records, and era trailer. The graph still draws straight segments and does not render saved curve types or tension modes. The API and CLI can create a Playlist Automation Clip by copying an existing type-5-targeted Playlist record, changing its established position, target, length, and track fields, and retaining its remaining bytes. The Playlist toolbar adds the selected Automation channel after the arrangement ends, choosing a length at least one measure long and long enough to include its last point. Creation requires an existing `0xEA` point blob and a saved Automation Clip template in the project. Creating `0xEA` blobs from scratch, decoding target-parameter links or legacy event automation, and creating generic parameter links remain incomplete.

Invalid ranges and duplicate Level Adjusts records are ignored. Mod X/Mod Y and VST3 descendants remain unapplied. ## Project Master pitch

Image-Line documents Master pitch as a per-project control that affects instruments and Audio Clips when their channel has **Enable main pitch** selected ([Toolbar manual](https://www.image-line.com/fl-studio-learning-content/fl-studio-online-manual/html/toolbar_panels.htm)). PyFLP maps the project value to a signed 16-bit word event `0x50` (`WORD + 16`) and documents the range as −1200 to +1200 cents ([PyFLP project parser](https://pyflp.readthedocs.io/en/latest/_modules/pyflp/project.html)). `ProjectMetadata` reads a unique global event, `ProjectSettingsEdit` and the desktop dialog can update it, and `set-project-master-pitch` writes it without changing other events. An absent event means zero cents; duplicate or malformed global events are not treated as a unique value. PyFLP maps Channel Parameters byte 12 (zero-based payload offset 11) to `Enable main pitch` and byte 64 to `Add to Key`; the model reads both, and API, Channel Rack, and CLI edits preserve other Parameters bytes ([PyFLP channel parser](https://github.com/demberto/PyFLP/blob/master/pyflp/channel.py)). Image-Line documents that Add to Key ON transposes note input by the Root Key offset, while OFF transposes source samples ([Channel Settings manual](https://www.image-line.com/fl-studio-learning-content/fl-studio-online-manual/html/chansettings_misc.htm)). When Enable main pitch is set, Playlist and pattern Sampler playback/rendering add Master pitch to sample source tuning if Add to Key is off; with Add to Key on, supported Sampler notes transpose by the nearest semitone. Unstretched Playlist Audio Clips with an unset or unit scale and clips using Resample mode change sample playback rate when enabled. For supported duration-preserving Stretch and Elastique 3 Generic clips, Master pitch and channel Fine Tune are combined with the saved stretch pitch before processing, so the clip keeps its target duration. Hosted VST3 pattern and Playlist note-on/off events use Master pitch as per-note tuning when enabled and Add to Key is off; with Add to Key on, note keys transpose by the nearest semitone; the VST3 SDK defines `+1` as `+1` cent ([NoteOnEvent documentation](https://steinbergmedia.github.io/vst3_doc/vstinterfaces/structSteinberg_1_1Vst_1_1NoteOnEvent.html)). Add to Key applies saved Sampler Root Key offsets to note input relative to the sample root and transposes enabled Master Pitch by the nearest semitone for supported Sampler and hosted VST3 notes; VST3 Root Key offsets and native instrument behavior remain incomplete, and native comparison is open. Native instruments remain incomplete; stretched Audio Clip pitch behavior uses the local processor and has not been compared with native FL Studio output. These paths have not been compared against a native FL Studio render; this checkout has no native FL Studio save/reopen fixture for the event mapping or pitch behavior.

## Mixer observations

In the installed NewStuff project, the Mixer-like section follows the 500 Playlist track records. Twenty-six repeated candidate insert records begin with consecutive four-byte events `0x9A`, `0x93`, and `0x95`. A `0x5F` two-byte field appears on some records, and the first following `0xCC` string yields names such as `KICK`, `TOMS`, `HI TOM`, and `Synth Bass`. The model exposes those strings plus the raw values and record boundaries. Existing `0xCC` names can be renamed while retaining their string encoding, terminator convention, and trailing bytes. The labels are plausible insert names, but a controlled UI comparison is still needed to confirm every field's displayed meaning and order across versions.

NewStuff also contains one `0xE1` data event with 11,220 payload bytes, exactly 935 records of 12 bytes each. The Rust model retains every record's raw fields, recognizes parameter IDs used for volume, pan, stereo separation, route volume, and three-band EQ, and can edit the signed value at an exact event/record index without touching the rest of the record. An independent parser interprets bits 6–12 of `channel_data` as a target index and bits 0–5 as a slot index; its open format question treats the top three bits as a possible scope field, so Rust exposes those bits raw. In the installed corpus, for the 65 projects with recognized named insert records, 1,751 of 1,882 named insert ordinals had matching volume and pan records at candidate target index `64 + ordinal`. The desktop now shows per-strip candidate controls only when that target has one volume and one pan record with zero scope bits: a raw vertical volume slider in the observed 0–16,000 range and a linear pan slider in the observed −6,400–6,400 range ([PyFLP Mixer parameter model](https://github.com/demberto/PyFLP/blob/master/pyflp/mixer.py)). A unique zero-scope stereo-separation record in the raw −64..64 range also gets an editable slider, and edits target the exact event and record indices. For supported direct Mixer routes, raw 0 leaves the side signal unchanged, +64 removes it to produce mono, and −64 doubles it using a local mid/side transform. Image-Line documents the center position as disabled, right as mono, and left as increased separation; PyFLP records the numeric range and sign ([Image-Line Mixer manual](https://www.image-line.com/fl-studio-learning/fl-studio-online-manual/html/mixer.htm), [PyFLP Mixer parameter model](https://github.com/demberto/PyFLP/blob/master/pyflp/mixer.py)). The Mixer inspector also exposes each insert’s unique zero-scope three-band EQ gain, frequency, and Q values as raw controls, with CLI/API edits limited to gain −1800…1800 and frequency/Q 0…65536. Frequency is nonlinear; duplicate and scoped EQ records remain unavailable, and the controls edit saved values without processing audio. Duplicate, missing, nonzero-scope, and out-of-range volume/pan/separation records remain available only in the raw inspector. The candidate-to-visible-track mapping still needs controlled native save comparison; supported insert-to-insert sends use provisional destination/gain mappings; loaded VST3 insert effects now process in the paths described below using dedicated pre-effect buses; the Master and recognized direct-route insert meters are available during live Playlist playback.

The candidate parameter IDs and target/slot split follow the independent [PyFLP Mixer parser](https://github.com/demberto/PyFLP/blob/master/pyflp/mixer.py). The meaning of the top three target bits remains an open question in [PyFLP issue 193](https://github.com/demberto/PyFLP/issues/193).

PyFLP defines `DATA` as 208 (`0xD0`), so its Mixer parameter event `DATA + 17` is `0xE1` and its per-insert routing event `DATA + 27` is `0xEB`. PyFLP parses each `0xEB` payload as byte-sized routing booleans and pairs those flags in order with the insert's `0xE1` route-volume records (IDs 64–191). The Rust Mixer inspector shows the paired on/off state and raw parameter ID/level for unambiguous candidate source inserts; unique flags and route levels can now be edited in place while retaining other event bytes. Duplicate parameter IDs and route records without a matching flag stay unpaired. The inspector does not label a destination track or send audio: the parameter-to-destination mapping has not been confirmed against a controlled native save. This follows PyFLP's event IDs where the independent [FLPDiff specification](https://github.com/dawhubapp/flpdiff/blob/main/docs/fl-format/flp-format-spec.md) currently labels `0xE7` as insert routing; `0xE7` is also a project-level text event in this parser, so the discrepancy needs native verification before using it for audio routing.

The clean-room [FLP format specification](https://github.com/dawhubapp/flpdiff/blob/main/docs/fl-format/flp-format-spec.md) reports ten `0x62` Mixer effect-slot markers per insert, in zero-through-nine order. The first marker precedes slot zero's accumulated events; markers one through nine close slots zero through eight, and the following `0x93` flushes slot nine when present. The preceding `0xC9` plug-in class, `0xCB` display name, and opaque `0xD5` state event remain byte-exact. The Mixer inspector shows recognized names and state-event counts without opening or changing the payload. FL Studio documents up to ten effects per Mixer track ([Mixer manual](https://www.image-line.com/fl-studio-learning/fl-studio-online-manual/html/mixer.htm)); matching installed VST3 effects can restore supported marker-12 state, apply saved bypass/Mix controls, and process in slot order. Reordering, editing chain contents, other plug-in formats, and native comparison remain incomplete.

An independent FL 25 byte-sweep specification records Mixer track flags in a 12-byte data event: `0xEC` on FL 25 and later, `0xDC` on earlier versions, with the flag word at payload offset 4 ([format reference](https://github.com/dawhubapp/flpdiff/blob/main/docs/fl-format/flp-format-spec.md)). The Rust model reads the observed enabled/mute bit (3), solo bit (12), polarity bit (0), left/right swap bit (1), and effects-enable bit (2), and the API can edit those bits while retaining reserved bytes and unknown flag bits. The Mixer inspector displays these saved states. Live Playlist playback and full-song WAV rendering apply Master mute, polarity, and stereo swap after mixing supported sources; recognized insert mute/solo state filters directly assigned source channels, while insert polarity and stereo swap transform them before they are mixed. Unique zero-scope candidate fader values with the observed `64 + insert ordinal` target convention now scale directly routed sources as provisional raw/10,000 gain, and the Master candidate fader scales the final mix. ## Compatibility limits

- The container reader parsed the installed corpus, but the semantic mappings above still come from a small number of inspected files. External projects, damaged files, and the earliest project versions remain unverified.
- Most event payload meanings remain unknown. Unknown events are retained byte-for-byte so later semantic support can be added without discarding data.
- VST3 hosting, editor integration, parameter access, a single-pattern/channel offline render path, marker-12 FLP VST3 component/controller restore and save-back, and explicit pattern-relative VST3 parameter lanes exist as prototypes. - The base tempo field at `0x9C` is confirmed as milli-BPM by changing an empty project's value from 140,000 to 100,000 and observing 100 BPM in FL Studio's MIDI export. Time-signature fields `0x11` and `0x12` still need controlled-save confirmation. NewStuff contains a separate channel named `TEMPO`; its automation payload is not yet decoded.

## Channel time-stretch settings

PyFLP maps the channel Parameters (`0xC7`) payload's four time-stretch fields at byte offsets 100, 104, 108, and 112 to time, pitch, multiplier, and mode respectively. The Rust channel summary exposes these values in their stored integer units when the payload contains all four fields, and the API and CLI can edit a selected subset in one unique, sufficiently long Parameters event while retaining every other byte. The CLI rejects undocumented mode values; known values are `-1` Stretch, `0` Resample, `1` Elastique 3 Generic, `2` Elastique 3 Mono, `3` Slice Stretch, `4` Slice Map, `5` Auto, and `6`–`9` Elastique 2 variants. These offsets and mode codes are cross-checked against [PyFLP's channel parser](https://github.com/demberto/PyFLP/blob/master/pyflp/channel.py). Playlist Audio Clip playback and rendering apply nonzero channel `TIME` settings for modes `-1`, `0`, and `1`, plus mode `2` for mono sources (the mono restriction is inferred from the mode name and still needs native confirmation): raw `TIME` converts to PPQ ticks as `raw * PPQ / 192`, `MUL` converts to a factor of `2^(raw/10000)`, and `PITCH` is cents. Stretch and Elastique 3 Generic use the local offline processor, limited to 0.5×–2×; Elastique 3 Mono uses the same duration-preserving processor for mono sources only; Resample changes playback rate with pitch. Scheduled Playlist Sampler notes apply Resample settings at each note's start tempo, and direct live Sampler MIDI input during Playlist playback uses the transport tempo at note-on; each voice retains the rate calculated when it started. Pattern Sampler playback and live Pattern audition use project tempo. Sampler Stretch and Elastique 3 Generic preprocess mono/stereo sources at a stable tempo with the local offline processor for 0.5×–2× ratios, preserve processed duration while applying channel pitch, and scale WAVE/AIFF loop bounds. Sampler Elastique 3 Mono uses this processor only for mono sources; the mono restriction is inferred from the mode name and still needs native confirmation. Scheduled Playlist notes reject tempo changes during the stretched source or while a loop remains held, and reject differing start tempos for one shared stretched source. Direct live Sampler MIDI input rejects tempo changes that would require rebuilding that source; other modes are rejected as unsupported. Only mono/stereo sources are handled. Playlist clip-level scale and native per-instance serialization remain unsupported. App-local instance settings can fit a clip to its visible duration using the Audio Clip channel's shared Resample, Stretch, or E3 mode and apply ±1200-cent pitch; the local processor and mode mapping still need native comparison. The unit conversions follow PyFLP's `LinearMusical` and `Log2` adapters and field documentation; no controlled native comparison has been made.

## Channel Fine Tune

PyFLP maps channel Fine Tune to dword event `0x8E` as a signed integer and documents values from -100 to +100 cents. Image-Line describes the channel control as tuning the sample's base note in cents ([PyFLP channel reference](https://pyflp.readthedocs.io/en/v2.1.0/reference/channel/channel.html), [Channel Settings manual](https://www.image-line.com/fl-studio-learning/fl-studio-online-manual/html/chansettings_misc.htm)). The Rust model retains the signed raw value and exposes values in that range; the API, CLI, and Channel Rack can edit it without rewriting unrelated events. Supported Sampler note playback/rendering adds channel Fine Tune to sample metadata tuning; Audio Clip playback/rendering applies the channel value directly to pitch. Both also apply enabled project Master pitch. Hosted VST3 channel Fine Tune joins project Master pitch for pattern preview, Playlist and Performance playback, and project renders. Native FL instrument tuning and native save/render comparison remain incomplete.
